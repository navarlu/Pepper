\section{Hardware Platform}
\label{sec:hardware}

The system runs on a small computer placed next to Pepper.
This computer hosts the services that make the receptionist work, provides the wireless network that Pepper joins, and reaches out to a remote GPU server when the language model needs to be run.

\subsection{Pepper Humanoid Robot}
\label{sec:pepper_robot}

Pepper is a 1.2~m semi-humanoid robot manufactured by SoftBank Robotics~\cite{pandey2018pepper}, equipped with an onboard Intel Atom computer running NAOqi~OS.
Programmatic access to the robot is provided through the \texttt{qi} framework.

For the receptionist scenario the following Pepper capabilities are used:
\begin{itemize}
    \item \textbf{Speakers} in the ears, addressed through NAOqi's audio device service for spoken-response playback.
    \item \textbf{Tablet} (chest-mounted touchscreen, with a diagonal of about 25~cm), used to display the current dialogue state, a live transcript, and the farewell QR code linking to the experiment questionnaire.
    \item \textbf{Animation player}, used to dispatch one of the predefined gesture sequences during each spoken reply.
\end{itemize}

Pepper's autonomous-life service is left enabled during the idle state so that the robot makes small natural head and body movements while waiting for a visitor; this gives a more lifelike presence than a fully static pose.
During an active dialogue the head is locked to a forward-and-slightly-upward pose, which gives a stable apparent gaze in the direction of the visitor and avoids distracting micro-movements while she is speaking.

The robot's onboard microphones are \emph{not} used in this deployment.
The built-in array is not robust enough for the receptionist setting, a limitation observed in prior work with the platform.
Speech input is captured instead with an external USB microphone (DJI~Mic) connected to the Raspberry Pi.
The precise placement of the microphone in the deployment is described together with the experimental procedure in \secref{sec:exp_procedure}.

A second deployment-specific workaround concerns the boot sequence of the particular Pepper unit used in this work.
One of the bottom laser-range sensors developed a fault during the project, which caused the start-up self-test to fail and prevented the robot from entering its normal operating state.
The \texttt{safe-startup} service (\tabref{tab:services}) intercepts the boot sequence, suppresses the offending self-test, and clears the resulting error notification so that the red shoulder LEDs stop blinking.
This is a workaround for a hardware fault on the specific unit rather than part of the system design.

\subsection{Compute Infrastructure}
\label{sec:compute_infra}

Two compute nodes run the system, in addition to Pepper itself:

\begin{enumerate}
    \item \textbf{Raspberry Pi~5 (8\,GB)} sits next to Pepper at the reception desk.
    It runs a local wireless hotspot that Pepper joins on startup, and it is also connected to the faculty network.
    The Raspberry Pi hosts most of the deployed system: the LiveKit media server, the supporting services (robot bridge, audio bridge, user-client capture, tablet server, experiment orchestrator, startup watchdog, vector database, state backend), and the experimental session driver \texttt{loop\_launcher.py}.

    \item \textbf{A departmental GPU server}, reachable through the faculty network.
    It hosts both voice agents --- the local cascade described in \secref{sec:local_mode} and the cloud cascade described in \secref{sec:cloud_mode} --- together with a vLLM~\cite{kwon2023vllm} server running Llama~3.1~8B Instruct~\cite{grattafiori2024llama3} on a localhost port; vLLM is used by the local cascade for language-model inference.
\end{enumerate}

Because the GPU server cannot open an inbound connection to the Raspberry Pi over the faculty network, an \texttt{autossh}-managed reverse SSH tunnel is opened from the Raspberry Pi.
The LiveKit ports are forwarded over this tunnel so that the voice-agent processes on the GPU server can join the LiveKit media server running on the Raspberry Pi.

The two-node split is driven by the local cascade, which needs GPU resources that only the departmental server provides.
The cloud cascade is hosted on the same machine for operational convenience and uniformity across conditions.

\section{System Architecture}
\label{sec:architecture}

The system is built as a set of loosely coupled services that communicate through three transports.
The decomposition was driven by three practical needs: runtime isolation of components with conflicting Python dependencies (in particular the \texttt{qi} bindings for Pepper, which are tied to a specific Python version and platform-specific native libraries), independent restartability during development and demonstrations, and the ability to run the local-side voice agent on a different physical machine than the rest of the stack.

\subsection{Communication Model}
\label{sec:communication_model}

Three transports bind the services together, each chosen for what it does well:

\begin{enumerate}
    \item \textbf{WebRTC via LiveKit.}
    All real-time audio between the visitor, the voice agent, and the robot passes through the LiveKit media server.
    The user-client publishes the microphone audio into the room, the active voice agent subscribes to it, the agent publishes its synthesised reply, and the audio-bridge subscribes to the agent's reply track on Pepper's behalf.
    LiveKit was chosen for its built-in acoustic echo cancellation, codec handling, room-level participant management, and data-channel support for short control messages.

    \item \textbf{HTTP REST.}
    Tool calls from the language model, gesture dispatch, tablet updates, and miscellaneous control commands all use synchronous HTTP.
    The robot-control endpoints (\texttt{/animation}, \texttt{/tablet/*}, \texttt{/led/*}, \texttt{/head/lock}, \texttt{/audio/volume}) are served by the bridge on a local port.
    Handlers validate the request, dispatch the action in a background thread, and return an immediate acknowledgement so that gesture dispatch does not block the current dialogue turn.

    \item \textbf{Raw TCP.}
    Audio playback on Pepper uses a custom length-prefixed protocol between the audio-bridge and the bridge.
    The bridge buffers 16-bit PCM frames and feeds them into NAOqi's audio device service.
    A short request/acknowledgement handshake at end-of-utterance lets the agent know when Pepper has finished speaking, which is needed so that the next user turn is not opened while audio is still playing out.
\end{enumerate}

\section{Voice Interaction Pipeline}
\label{sec:voice_pipeline}

The system supports two voice interaction backends, the two compared in this work.
Both expose the same tool interface, session lifecycle, and robot-control interface to the rest of the architecture; they differ in \emph{where} the speech is processed and \emph{which} language model handles the dialogue.

Both backends are cascaded pipelines: a voice activity detector segments the user's turn, a speech-to-text component transcribes the utterance, a language model produces the reply, and a text-to-speech component synthesises the audio.
End-to-end speech-to-speech models such as Moshi~\cite{defossez2024moshi} or the OpenAI Realtime API are an alternative architecture and would be valid choices for either condition, but using cascades for both conditions isolates the local-versus-cloud comparison from any confound introduced by an architectural difference between the two.

Both worker processes are built on the LiveKit Agents SDK and share most of their wiring through a common pipeline-construction routine: the same agent class, the same tool surface, the same recording schema.
They differ only in the concrete component instances chosen when the pipeline is built.
They register with LiveKit under different agent names so that the session driver can dispatch the correct one for each visitor.

\subsection{Condition~A: Local Cascade}
\label{sec:local_mode}

The local cascade runs on the GPU server.
Its components are:

\begin{itemize}
    \item \textbf{Voice activity detection.} Silero VAD, used to segment the user's turn.
    \item \textbf{Speech-to-text.} \texttt{faster-whisper}~\cite{radford2023whisper}, an optimised CTranslate2 port of OpenAI's Whisper, running with the \texttt{tiny} model and INT8 quantisation as the default configuration.
    \item \textbf{Language model.} Llama~3.1~8B Instruct~\cite{grattafiori2024llama3}, AWQ-quantised and served by vLLM~\cite{kwon2023vllm} at a localhost port.
    The model is reached from the agent process over the OpenAI-compatible REST API exposed by vLLM.
    \item \textbf{Text-to-speech.} Piper, a fast neural TTS engine based on VITS, running an English female voice in ONNX format.
\end{itemize}

The agent process reaches the LiveKit media server on the Raspberry Pi through the reverse SSH tunnel described in \secref{sec:compute_infra}; LiveKit's TURN relay (TLS over TCP) is used to transport the WebRTC media, because SSH does not forward UDP natively.

Earlier development used Qwen~2.5~7B as the local language model, which required several application-level workarounds to reach acceptable tool-calling reliability: JSON-argument sanitisation, careful tool-docstring phrasing, and single-line system prompts that the parser would not choke on.
Llama~3.1~8B handles the same tool surface without most of these workarounds, although a defensive JSON-sanitisation patch is still installed for safety.
The Berkeley Function Calling Leaderboard~\cite{patil2025bfcl} places Llama~3.1~8B Instruct in the upper range of tool-calling-capable open models at this size, which was the main reason for the switch.

\subsection{Condition~B: Cloud Cascade}
\label{sec:cloud_mode}

The cloud cascade runs on the same GPU server as Condition~A.
Its components are:

\begin{itemize}
    \item \textbf{Voice activity detection.} The same Silero VAD configuration as Condition~A.
    \item \textbf{Speech-to-text.} OpenAI \texttt{gpt-4o-mini-transcribe}.
    \item \textbf{Language model.} OpenAI \texttt{gpt-4o-mini}, reached over the standard OpenAI REST API.
    \item \textbf{Text-to-speech.} OpenAI \texttt{gpt-4o-mini-tts}, using the \texttt{nova} voice with a short instruction asking the model to speak in a warm, conversational receptionist tone.
\end{itemize}

The cloud cascade shares every other element of the pipeline with Condition~A: the same tool definitions, the same system prompt, the same session lifecycle, and the same recording schema.
The only external dependency that differs is the OpenAI API itself, which adds variable network latency depending on server load.

\subsection{Turn-Taking}
\label{sec:turn_taking}

Both backends use Silero VAD to determine when the user has finished speaking.
Once the VAD declares end-of-turn, the cascade runs to completion before the agent listens again.
The agent session is explicitly configured to disallow interruptions: user speech captured while Pepper is talking is discarded rather than cutting her off.
The only intentional barge-in is an operator command on a dedicated data channel, which lets the experimenter inject a typed utterance during the session if Pepper needs to be redirected.

\section{Agent Tools and Knowledge Sources}
\label{sec:knowledge}

The agent's behaviour is shaped by two things: a \emph{system prompt} that tells the language model who Pepper is and how to behave, and a \emph{tool surface} that lets the language model act on the world.
These two surfaces are the only places where domain knowledge and persona live in the system; the rest of the pipeline --- the speech components, the LiveKit transport, the robot bridge, the session driver --- is plumbing that does not change when the agent is adapted to a different scenario.
Adding a new ability (a database lookup, a new robot motion, an integration with a third-party service) is a matter of writing a tool and naming it in the prompt; changing the persona is a matter of editing the prompt's identity and personality sections.
This separation is a deliberate design choice and is the main reason the same code path supports two interchangeable backends without changes elsewhere in the system.


\subsection{System Prompt}
\label{sec:system_prompt}

The system prompt is a single text document that tells the language model who Pepper is, what tools are available, how to use them, and how to phrase its replies.
It is organised into named sections so that any one of them can be revised without disturbing the others:

\begin{itemize}
    \item \textbf{Identity} --- the robot's persona and the institutional setting.
    \item \textbf{Personality} --- the tone the model should adopt (warm, brief, slightly playful, not a search engine).
    \item \textbf{Hard-coded facts} --- a short list of facility facts that are stable enough and short enough to inline (example room codes such as \texttt{E-107}), so that the model does not waste a tool call on them.
    \item \textbf{Communication model} --- the critical rule that plain assistant text is never heard by the visitor; only the \texttt{text} argument of \texttt{send\_message\_to\_user} is spoken.
    \item \textbf{Body language vocabulary} --- the enumerated emotion labels (see \secref{sec:animations}) with a one-line intent for each.
    \item \textbf{Reply style} --- output-formatting rules (one or two short sentences, plain conversational prose, no markdown or stage directions).
    \item \textbf{Closing the conversation} --- when to call \texttt{end\_conversation} and how to phrase the farewell.
\end{itemize}

A second, much shorter, block of greeting instructions is merged into the system prompt only on the first user turn of a session.
It tells the agent to open with a fixed greeting line and the appropriate gesture; from the second turn onward this block is dropped, which keeps the prompt context tidy and prevents the model from re-greeting the same visitor.

\label{sec:tool_surface}

Both Condition~A and Condition~B see exactly the same tool surface so that the resulting transcripts are directly comparable.
Each tool's docstring carries a positive-framing trigger of the form ``call \emph{tool-name} when the user asks for X'', which the language model uses to decide when the tool is the right thing to call.

A Weaviate vector database is provisioned in the deployment with the intention of supporting retrieval-augmented generation over an institutional document corpus, but the live tool surface used in the experiment does not query it.
The reasoning behind a small, sharply-typed tool surface is twofold.
First, the dominant queries a faculty visitor brings to the desk --- a room, a person, a lecture, lunch --- all have an underlying authoritative source that is easier and more accurate to query directly than to summarise from a vector index.
Second, a smaller and more sharply-typed surface keeps tool-call reliability high on a local 8B-parameter model: each tool's docstring carries a clear ``call when X'' trigger that the model complies with reliably, whereas a single broad-trigger search tool tends to be over-fired and to hijack early turns.

\paragraph{Dispatch and multi-step reasoning.}
A tool call from the language model goes through the LiveKit Agents framework: arguments are deserialised against a schema derived from the Python type annotations, the tool coroutine runs, and the structured return value is fed back into the model context as a tool-result message.
Tools that return information return a dictionary; tools that terminate the turn --- such as \texttt{send\_message\_to\_user} and \texttt{end\_conversation} --- return nothing and end the turn.
This two-state distinction between non-terminal and terminal tools is inspired by the request-heartbeat pattern introduced in the Letta agent framework~\cite{packer2023memgpt}, implemented here as a thin wrapper on top of the LiveKit Agents SDK.
The agent session is capped at four tool calls per visitor turn, which bounds runaway tool chaining without preventing the typical pattern of one lookup followed by one spoken reply.
Two operations run in the background: gesture dispatch (see \secref{sec:nonverbal}) is fire-and-forget so the agent does not wait for the animation to finish, and for the tools that hit external HTTP endpoints a short filler utterance (``Let me check'') is dispatched in parallel with the network call so the visitor hears immediate audio feedback while the lookup is in flight.

\paragraph{Failure handling.}
Every tool that can fail returns a structured payload with an \texttt{error} field and an \texttt{instruction} field telling the language model how to phrase the failure --- for example, room-not-found yields an instruction to ask the visitor to confirm the room code.
The language model paraphrases the instruction and speaks the result through \texttt{send\_message\_to\_user}.
There is no automatic fallback to a free language-model answer when an external service is down: the failure mode is always an explicit apology or follow-up question rather than a fabricated reply.

\section{Non-Verbal Behaviour}
\label{sec:nonverbal}

\subsection{Gestures}
\label{sec:animations}

Pepper accompanies every reply with a short body gesture.
Rather than expose a separate \texttt{play\_animation} tool to the language model, the gesture is bound to the act of speaking: every tool in the speaking and lookup surface takes an extra \texttt{emotion} argument of an enumerated type.
When the language model calls one of these tools, the agent picks a random concrete animation from the group corresponding to the chosen emotion and sends an HTTP request to the robot bridge, which plays it through NAOqi's animation player.
The gesture dispatch is a fire-and-forget background coroutine, so the agent does not wait for the animation to finish before continuing with the spoken reply.

Binding the gesture to the spoken tool call --- rather than to a separate tool --- has two practical consequences.
First, the language model cannot speak without specifying an emotion, which makes gesture coverage essentially complete: every reply is accompanied by some movement.
Second, the gesture is chosen by the same reasoning step that decides what to say, so the emotion label and the spoken content are produced in a single language-model turn rather than in two consecutive turns that the model would have to keep in sync.

Fifteen emotion labels are currently exposed to the language model.
They cover social openings and closings (\texttt{greet}, \texttt{bow}, \texttt{goodbye}); short reactions (\texttt{affirm}, \texttt{deny}, \texttt{question}); cognitive states the robot wants to show (\texttt{think}, \texttt{dont\_know}); explanatory dialogue (\texttt{explain}, \texttt{emphasis}, \texttt{offer}, \texttt{address\_user}, \texttt{calm}); a softer \texttt{whisper} variant; and a \texttt{speak\_neutral} fallback for routine speech.
Each label maps to a group of concrete Pepper animation sequences (e.g.\ several variants of a greeting wave), and the variant is picked uniformly at random when the gesture fires.
The random pick avoids the obvious repetition that a single canonical animation per label would produce.
Only silent animations are used: variants that embed canned vocalisations were excluded so as not to clash with the synthesised speech.


\subsection{Tablet}
\label{sec:tablet}

Pepper's chest-mounted tablet is used as a secondary visual channel.
During a session it displays:

\begin{itemize}
    \item The session's participant code shown as a small chip at the top of the screen, used to link this session's log with the questionnaire response (see \secref{sec:exp_procedure}).
    \item A current-state indicator (listening, thinking, speaking) that updates as the dialogue progresses, plus a small ``mic muted'' indicator when the microphone is not currently accepting speech.
    \item A live transcript of the conversation, showing both the visitor's recognised speech and Pepper's replies.
    \item At the end of the session, a QR code linking to the experiment questionnaire, pre-filled with the participant code so the visitor does not have to type it. A short countdown is shown alongside the QR so that it stays visible for a known interval after the conversation ends.
\end{itemize}

The tablet state is owned by the \texttt{tablet-server} service, which renders the appropriate HTML and sends it to the bridge as a \texttt{data:text/html} payload.
The bridge in turn pushes the HTML to NAOqi's tablet service, which renders it on the on-device browser.

\section{Session Management and Orchestration}
\label{sec:orchestration}

\subsection{Session Lifecycle}
\label{sec:session_lifecycle}

A receptionist session is the unit of interaction with a single visitor.
Sessions proceed through three states:

\begin{enumerate}
    \item \textbf{Idle.}
    No visitor is in the room.
    The voice-agent worker for the currently scheduled condition is connected to the LiveKit room as a warm participant: speech-processing models are loaded, the LiveKit transport is established, and the agent is waiting for an activation signal.

    \item \textbf{Active.}
    A visitor is present.
    The session driver sends an activation signal to the agent over a LiveKit data channel, the agent greets the visitor, and dialogue begins.

    \item \textbf{Reset.}
    The visitor leaves, the agent calls its \texttt{end\_conversation} tool, or a silence timeout elapses.
    The current worker is shut down and the session driver dispatches a fresh worker for the next scheduled condition.
\end{enumerate}

The warm-agent design is a deliberate choice driven by first-response latency.
Loading the speech-processing models takes several seconds on the target hardware; keeping the agent process alive across the idle state amortises this cost so that the first reply after a visitor arrives is fast.

\subsection{Experimental Loop}
\label{sec:experiment_loop}

For the experiment, sessions are dispatched in a loop on the Raspberry Pi by the script \texttt{loop\_launcher.py}.
The loop runs one session at a time, alternates the assigned condition between sessions (Condition~A and Condition~B in alternation), and persists the next-up condition and student identifier to a small JSON state file so the loop can resume after a restart.
A heartbeat written every two seconds to the shared state file keeps Pepper awake during the experiment; if the loop is killed, the heartbeat ages out and Pepper falls asleep on her own.

Each session ends naturally when the agent fires \texttt{end\_conversation}, or after a silence timeout if the visitor walks away without a closing turn.
The next session begins as soon as the previous worker has exited cleanly.

\subsection{Audio Delivery to the Robot}
\label{sec:audio_delivery}

The voice agent generates synthesised speech inside the LiveKit room, but Pepper's speakers are not directly reachable from LiveKit.
The \texttt{audio-bridge} service closes this gap.
It joins the LiveKit room as a non-agent participant, subscribes to the active agent's audio track, resamples the PCM stream to 16~kHz mono (Pepper's expected input format), and forwards the frames over the raw TCP audio protocol to the bridge, which feeds them into NAOqi's audio device service for playback.
The audio-bridge follows the active agent automatically across condition switches: when the previous worker exits and the next worker joins the room, the subscription is redirected to the new audio track without manual intervention.

\section{Implementation and Deployment}
\label{sec:implementation}

All code is implemented in Python and orchestrated through Docker Compose.
Containers on the Raspberry Pi share a base image built on Python~3.12 with the \texttt{uv} package manager; the project source is bind-mounted into each container so that code changes are live on disk and require only a container restart, not an image rebuild.
The \texttt{qi} library required by the bridge to talk to Pepper is compiled from source for ARM64 and supplied as a host-mounted volume because no pre-built package exists for this platform.

Bringing the system up from scratch requires the Raspberry Pi to be provisioned with the \texttt{qi} library, an \texttt{.env} file with the required API keys, and an SSH key authorised for the faculty jump host.
Once those prerequisites are in place, the deployment reduces to three commands: bringing up the Compose stack on the Raspberry Pi, starting the vLLM server and both voice agents on the GPU server under \texttt{tmux}, and launching the session driver on the Raspberry Pi.
Full setup instructions, configuration details, and the exact command sequence are kept in the project repository~\cite{github-repo-thesis}; see Appendix~A.
