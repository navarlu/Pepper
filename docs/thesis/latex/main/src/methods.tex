\section{System Overview}
\label{sec:system_overview}

The deployed system spans three physical machines (Figure~\ref{fig:architecture}).
A Raspberry~Pi~5 is located next to Pepper at the reception desk and hosts most of the supporting services: the LiveKit media server (see \secref{sec:communication_model}), the robot \texttt{bridge} that talks to NAOqi (see \secref{sec:pepper_robot}), an \texttt{audio-bridge} that pipes synthesized speech onto Pepper's speakers, a \texttt{user-client} that captures the visitor's microphone, a \texttt{tablet-server} that renders the on-chest tablet, the \texttt{experiment-orchestrator}, a per-session driver, and a few utility services (startup watchdog, reverse SSH tunnel, vector database).
A departmental GPU server hosts the language-model inference (vLLM serving Llama~3.1~8B Instruct) and runs the two voice-agent processes themselves.
Pepper itself embodies the agent: its speakers carry the synthesized voice, its chest tablet displays dialogue state and tool results, and its animated body provides the gestures the visitor sees.

The split is driven by hardware: the local voice cascade needs a GPU that the Raspberry~Pi does not have, and the GPU server is on the faculty network which cannot reach the Raspberry~Pi inbound, so an \texttt{autossh}-managed reverse SSH tunnel is opened from the Raspberry~Pi to the GPU server and the LiveKit ports are forwarded back over it.
The cloud cascade is hosted on the same GPU server for operational uniformity, even though it does not need the GPU itself.

Three transports glue everything together: WebRTC via LiveKit for the real-time audio between the visitor, the voice agent, and the playback \texttt{bridge}; HTTP REST for tool calls, gesture dispatch, and tablet updates; and a long-lived SSH connection feeding \texttt{paplay} on Pepper for the actual playback (see \secref{sec:dec_audio}).

\section{Architecture Decisions}
\label{sec:arch_decisions}

This section explains the four design choices that most shaped the deployed system.
Each of them was made under a concrete constraint---latency, the location of microphone and speaker, or the assignment's requirements---and each has visible consequences in the rest of the chapter.

\subsection{Audio Playback}
\label{sec:dec_audio}

An earlier version of the audio bridge fed PCM frames over a TCP socket into NAOqi's \texttt{ALAudioDevice} service.
That path added roughly one second of playback buffer that could not be reduced from outside NAOqi, which dominated the perceived response time.
The deployed system therefore bypasses NAOqi for real-time TTS playback: the \texttt{audio-bridge} service spawns a persistent \texttt{ssh + paplay} subprocess into Pepper's PulseAudio daemon and writes the agent's synthesized audio directly to its stdin (\texttt{services/src/live/audio\_bridge.py}).

\subsection{Custom Acoustic Echo Cancellation}
\label{sec:dec_aec}

The microphone is on the visitor's side of the reception desk; the speakers are on Pepper, on the other side of a pane of glass.
Without echo cancellation, the microphone picks up Pepper's own voice loud enough that the voice activity detector treats it as a visitor turn, so the agent ends up replying to itself.
An early workaround was to mute the visitor's microphone while Pepper was speaking; this prevented the self-reply but made the interaction feel unnatural, because visitors could not interrupt or speak over her.
LiveKit's built-in echo cancellation would have been the obvious alternative, but it assumes that microphone and speaker share one physical device, which is not the case here.
Echo cancellation is therefore done in the \texttt{user-client} service before the microphone audio is published into the LiveKit room: a WebRTC AEC3 module is fed both the microphone capture and the agent's reply track as a reference, and the cleaned-up signal is what the speech-to-text component sees.
With the echo removed, the visitor can interrupt Pepper mid-reply without her own voice being mistaken for the interruption.

\subsection{Streaming Reply, Gestures via Tool Calls}
\label{sec:dec_streaming}

An earlier design followed the tool-only pattern of the Letta agent framework~\cite{packer2023memgpt}: the language model could only speak by calling a \texttt{send\_message\_to\_user} tool with the reply text and a gesture label as arguments.
This had the appealing property that every spoken sentence carried an explicit gesture chosen by the same reasoning step that produced the text, so the visible body language matched the words in a fine-grained way.
The problem was latency: a tool call cannot be issued until the language model has finished writing its arguments, so the entire reply text has to be generated before the text-to-speech component sees the first character.

The deployed system streams the reply directly: the language model emits tokens, the text-to-speech component consumes them as they arrive, and Pepper begins to speak as soon as the first sentence is ready.
Gestures still exist, but they are dispatched only when the model calls one of the non-speaking tools (\texttt{lookup}, \texttt{navigation}, \texttt{schedule}, \texttt{time}, \texttt{query\_search}, \texttt{end-of-conversation}), each of which takes an \texttt{emotion} argument.
The trade-off is honest: the surface of gesture intents is narrower than under the tool-only design---most gestures are now ``thinking'' on the way to a tool result, and the open-ended ``explaining'' or ``offering'' gestures that the older design could produce during the reply itself are missing.
First-audio latency was the deciding factor.

\subsection{Tools and Prompt as the Only Extension Points}
\label{sec:dec_extensibility}

Pepper's behavior and knowledge are defined entirely by two things: the system prompt and the set of registered tools.
Changing the persona means editing the identity and personality sections of the prompt; adding a new capability---a database lookup, a new robot motion, an integration with a third-party service---means writing one Python function, decorating it with the LiveKit Agents \texttt{@function\_tool} decorator, and naming it in the prompt.
Nothing else in the pipeline needs to change.

The same modularity extends to the dialogue model itself.
In Condition~A the language model runs on the GPU server under vLLM, and switching to a different local model is a matter of pointing vLLM at another checkpoint.
In Condition~B the cloud model is selected by a single configuration string, so swapping \texttt{gpt-4o-mini} for any other OpenAI chat-completion model is a one-line change.

\section{Hardware Platform}
\label{sec:hardware}

\subsection{Pepper}
\label{sec:pepper_robot}

\begin{wrapfigure}{r}{0.35\textwidth}
    \vspace{-0.5\baselineskip}
    \centering
    \includegraphics[width=0.33\textwidth]{src/figures/methods/pepper.png}
    \caption{The Pepper humanoid robot~\cite{pandey2018pepper}.}
    \label{fig:pepper}
\end{wrapfigure}
Pepper is a 1.2~m tall humanoid robot~\cite{pandey2018pepper}.
All on-board sensors, actuators, speakers, and the chest tablet are accessed through NAOqi, middleware that ships with the robot~\cite{naoqi_docs}.
The receptionist scenario uses Pepper's speakers, the chest-mounted tablet for the current-state display, and the animation player for gesture playback.
Pepper's autonomous-life service is left enabled while the robot is idle so that small head and body movements give a lifelike presence; during a session the head is locked to a forward-and-slightly-upward pose so that the apparent gaze stays on the visitor.

The robot's onboard microphone array is not used; speech is captured with an external USB microphone connected to the Raspberry~Pi.
One bottom laser-range sensor on the particular Pepper unit developed a fault during the project and caused the start-up self-test to fail; a small \texttt{safe-startup} service suppresses the offending check and clears the resulting error notification on every boot.

\subsection{Compute Infrastructure}
\label{sec:compute_infra}

Two compute nodes run the system in addition to Pepper itself:

\begin{enumerate}
    \item \textbf{Raspberry~Pi~5 8GB RAM.}
    Sits next to Pepper at the reception desk.
    It runs a local wireless hotspot that Pepper joins on startup, and is also connected to the faculty network.
    The Raspberry~Pi hosts the LiveKit media server, the supporting services listed in \tabref{tab:services}, and the per-session driver.

    \item \textbf{Departmental GPU server.}
    Reachable through the faculty network, equipped with an NVIDIA RTX~4000~SFF Ada Generation GPU~\cite{nvidia_rtx4000_sff}.
    It hosts both voice-agent processes---the local cascade described in \secref{sec:local_mode} and the cloud cascade described in \secref{sec:cloud_mode}---together with a vLLM~\cite{kwon2023vllm} server running Llama~3.1~8B Instruct~\cite{grattafiori2024llama3} that the local cascade calls.
\end{enumerate}

Because the GPU server cannot reach the Raspberry~Pi inbound, a reverse SSH tunnel is opened from the Raspberry~Pi.
The LiveKit ports are forwarded over this tunnel, and the audio path of \secref{sec:dec_audio} reuses the same SSH connection.

\label{sec:architecture}

The system is a set of loosely coupled services that talk to each other over three transports.
The decomposition was driven by two practical needs: independent restartability during development and demonstrations, and the ability to run the voice agents on a different physical machine from the rest of the stack.

\subsection{Communication}
\label{sec:communication_model}

Three transports bind the services together, each chosen for what it does well:

\begin{enumerate}
    \item \textbf{WebRTC via LiveKit.}
    LiveKit is an open-source WebRTC framework whose Agents SDK orchestrates the speech-to-text, language-model, and text-to-speech components and routes audio between the visitor and the agent~\cite{livekit_docs}.
    Real-time audio between the visitor's microphone, the voice agent, and the \texttt{audio-bridge} passes through the LiveKit media server.
    LiveKit was chosen for its room-level participant management and codec handling; echo cancellation is \emph{not} delegated to LiveKit and is performed in the \texttt{user-client} instead (see \secref{sec:dec_aec}).

    \item \textbf{HTTP REST.}
    Tool calls from the language model, gesture dispatch, tablet updates, and miscellaneous control commands all use synchronous HTTP to the \texttt{bridge}.

    \item \textbf{SSH + \texttt{paplay}.}
    The audio path from the agent's synthesized reply to Pepper's speakers, described in \secref{sec:dec_audio}.
\end{enumerate}

\section{Voice Interaction Pipeline}
\label{sec:voice_pipeline}

The system supports two voice interaction backends, the two compared in this work.
Both expose the same tool interface, session lifecycle, and robot-control interface to the rest of the architecture; they differ only in \emph{where} the speech is processed and \emph{which} models handle the dialogue.

Both backends are cascaded streaming pipelines: a voice activity detector segments the user's turn, a speech-to-text component transcribes the utterance, a language model generates the reply token by token, and a text-to-speech component synthesizes the audio incrementally so that Pepper begins to speak as soon as the first sentence is ready.
End-to-end speech-to-speech models such as Moshi~\cite{defossez2024moshi} or the OpenAI Realtime API are an alternative architecture.
Using cascades for both conditions is a study-design decision: it isolates the local-versus-cloud comparison from any confound introduced by an architectural difference between the two, and is not a claim that cascades are generally preferable to end-to-end audio models.

Both voice-agent worker processes are built on the LiveKit Agents SDK and share most of their wiring through a common pipeline-construction routine: the same agent class, the same tool surface, the same recording schema.
They differ only in the concrete component instances chosen when the pipeline is built, and they register with LiveKit under different agent names so that the session driver can dispatch the correct one for each visitor.

\subsection{Condition A: Local Cascade}
\label{sec:local_mode}

The local cascade runs on the GPU server.
Its components are:

\begin{itemize}
    \item \textbf{Voice activity detection.} A voice activity detector (VAD) flags whether each short audio frame contains speech, which lets the pipeline know when the visitor's turn starts and ends. We use Silero VAD~\cite{silero_vad}, a small open-source neural detector.
    \item \textbf{Speech-to-text.} \texttt{faster-whisper}~\cite{radford2023whisper}, a fast port of OpenAI's Whisper, running the small model.
    \item \textbf{Language model.} Llama~3.1~8B Instruct~\cite{grattafiori2024llama3}, served by vLLM~\cite{kwon2023vllm}. Llama~3.1~8B was chosen because it is the largest model that fits on the available GPU together with the speech components and because its tool-calling ability is competitive with small frontier models on the Berkeley Function Calling Leaderboard~\cite{patil2025bfcl}.
    \item \textbf{Text-to-speech.} Piper, a fast open neural TTS engine, with an English female voice.
\end{itemize}

\subsection{Condition B: Cloud Cascade}
\label{sec:cloud_mode}

The cloud cascade runs on the same GPU server as Condition~A; it does not use the GPU itself. So it could run on the Raspberry~Pi, but hosting it on the GPU server keeps the deployment more uniform and avoids adding extra load to the Raspberry~Pi.
Its components are:

\begin{itemize}
    \item \textbf{Voice activity detection.} The same Silero VAD configuration as Condition~A.
    \item \textbf{Speech-to-text.} OpenAI \texttt{gpt-4o-mini-transcribe}.
    \item \textbf{Language model.} OpenAI \texttt{gpt-4o-mini}, reached over the standard OpenAI REST API.
    \item \textbf{Text-to-speech.} OpenAI \texttt{gpt-4o-mini-tts}, using the \texttt{nova} voice with a short instruction asking the model to speak in a warm, conversational receptionist tone.
\end{itemize}


\subsection{Turn-Taking}
\label{sec:turn_taking}

Both backends use the voice activity detector to determine when the visitor has finished speaking.
Once end-of-turn is declared, the cascade generates a reply.
Visitors are free to interrupt Pepper mid-reply: with the echo cancellation of \secref{sec:dec_aec} in place, Pepper's own voice is removed from the captured microphone signal, so the voice activity detector can still pick out a genuine visitor utterance while Pepper is speaking and cut her off cleanly.

\section{Agent Behavior: Prompt and Tools}
\label{sec:knowledge}

The agent's behavior is shaped by two surfaces: a \emph{system prompt} that tells the language model who Pepper is and how to behave, and a \emph{tool surface} that lets the language model act on the world.
These two surfaces are the only places where domain knowledge and persona live; the rest of the pipeline is plumbing that does not change when the agent is adapted to a different scenario (see \secref{sec:dec_extensibility}).

\subsection{System Prompt}
\label{sec:system_prompt}

The system prompt is a single text document organized into three named sections:

\begin{itemize}
    \item \textbf{Identity, personality, and known facts}---who Pepper is, the tone she should adopt (warm, brief, slightly playful), and a short list of facility facts that are stable enough and short enough to include directly in the prompt (example room codes, opening hours of nearby facilities) so that she does not waste a tool call on them.
    \item \textbf{Reply style}---one or two short sentences, plain conversational prose, no markdown, no stage directions, and an explicit rule that the model never mentions tools or function names in its reply.
    \item \textbf{When to call tools}---a positive-framed trigger for each tool of the form ``call \emph{tool-name} when the user asks for X''.
\end{itemize}

The opening greeting is not part of the system prompt.
The moment a session starts, Pepper speaks a fixed greeting line directly through the text-to-speech component, before the language model is called at all.
During the experiment this turned out to be a mistake. The greeting plays unconditionally before the language model is involved, so a visitor who walked up and asked a question on the first turn got ``Hello, how can I help you today?'' instead of an answer.

\subsection{Tool Surface}
\label{sec:tool_surface}

The deployed agent exposes seven tools, listed in \tabref{tab:tools}.
Both Condition~A and Condition~B see exactly the same tool surface so that the resulting transcripts are directly comparable.

\centering

\hline

\hline
\texttt{find\_path\_to\_room} & Walking directions from the entrance to a given room code. & Manually prepared dictionary. \\
\texttt{lookup\_person} & Office, phone, and email of a staff member by surname. & Live HTTPS scrape of the public faculty directory. \\

The initial design used \texttt{query\_search} as the only knowledge backend: a Weaviate vector store would hold institutional documents and the agent would retrieve from them for any factual question.
This design was inspired by \emph{FELChat}~\cite{felchat-repo}, an earlier team project that answers questions from the same set of CTU and FEE documents, and the same corpus was uploaded into the Pepper deployment.

During development it became clear that the institutional information visitors actually need at a reception desk---room locations, staff contacts, course schedules, the canteen menu---is already available behind public faculty endpoints, and that fetching it directly is more reliable than retrieving paragraphs about it from a PDF.
The system was therefore extended with four targeted live HTTP endpoints---\texttt{find\_path\_to\_room}, \texttt{lookup\_person}, \texttt{subject\_schedule}, and \texttt{mensa\_menu}---that fetch the current data on demand and return short, prompt-friendly results.
The advantage over a static vector store is freshness: when a room is reassigned or a lecture moves to a different time, the next visitor automatically gets the new value with no maintenance step.

\texttt{query\_search} remains in the tool surface for what the live endpoints do not cover: domain-specific knowledge such as internal regulations, institutional procedures, or faculty-specific documents.
Extending Pepper along this axis is a single drop-in operation (details in the next paragraph).

The knowledge base used by \texttt{query\_search} is a small set of CTU and FEE official documents: the Czech Higher Education Act 111/1998 (English version), the CTU Statute, and the Accommodation, Career, Disciplinary, Scholarship, and Doctoral Study codes, together with one CTU rector's directive (SD 2015/02).
Each PDF is split into overlapping character chunks (3000 characters per chunk, 300-character overlap), and each chunk is stored as one Weaviate object together with its title, source file, and an OpenAI \texttt{text-embedding-3-large} vector---the eight source documents yield 329 chunks in total.
The OpenAI embedder was chosen for convenience and is interchangeable with a local model.
Retrieval is hybrid (vector + BM25) with a configurable mix parameter $\alpha = 0.7$, returning the top-$k$ chunks back to the language model as the tool result.
Adding a new document is intentionally a single operation: drop the PDF (or plain-text file) into \texttt{voice-agent/src/data/FEL/} and restart the agent---the seeding routine in \texttt{voice-agent/src/live/rag.py} ingests every new file on the next boot, so extending Pepper's institutional knowledge does not require touching any code.


A tool call from the language model goes through the LiveKit Agents framework: the tool runs, and its return value is fed back into the model context as a tool-result message.
Two operations run in the background: gesture dispatch (\secref{sec:nonverbal}) does not block the agent on the animation finishing, and for tools that hit external HTTP endpoints a short filler utterance (``Let me check'') is played in parallel with the network call so the visitor hears immediate audio feedback while the lookup is in flight.


Every tool that can fail returns a structured payload with an \texttt{error} field and an \texttt{instruction} field telling the language model how to phrase the failure. For example room-not-found yields an instruction to ask the visitor to confirm the room code.
The language model paraphrases the instruction in its next streamed sentence.
There is no automatic fallback to a free language-model answer when an external service is down: the failure mode is always an explicit apology or follow-up question rather than a fabricated reply.

\section{Non-Verbal Behaviour}
\label{sec:nonverbal}

\subsection{Gestures}
\label{sec:animations}

Pepper accompanies tool calls with a short body gesture.
Each non-speaking tool in the surface of \secref{sec:tool_surface} takes an extra \texttt{emotion} argument; when the language model calls the tool, the agent triggers the corresponding animation on Pepper without blocking on it.

Fifteen emotion labels are exposed to the language model.
They cover social openings and closings (greet, bow, goodbye), short reactions (affirm, deny, question), cognitive states the robot wants to show (think, don't-know), explanatory dialogue (explain, emphasis, offer, address-user, calm), and a neutral fallback.
Each label maps to a group of concrete animations, and the variant is picked at random on each call to avoid the obvious repetition that a single fixed animation per label would produce.
Only silent animations are used so that canned vocalizations do not clash with the synthesized speech.

Because gestures fire on tool calls rather than on the streamed reply (\secref{sec:dec_streaming}), the gestures actually seen during a session lean toward the ``thinking'' and ``looking up'' part of the emotion vocabulary; the more expressive ``explaining'', ``offering'', or ``emphasizing'' gestures that the abandoned tool-only design could produce during the spoken reply itself are absent.
This is a known trade-off in favour of streaming latency.

\subsection{Tablet}
\label{sec:tablet}

Pepper's chest-mounted tablet is used as a secondary visual channel.
During a session it shows a live transcript of the conversation---both what Pepper heard the visitor say and what Pepper said back---so the visitor can check that her question was understood correctly.
When a tool returns concrete data such as a phone number, an office number, or a course code, that data stays on the tablet after Pepper has finished speaking, which gives the visitor time to read it or write it down.

The tablet state is owned by the \texttt{tablet-server} service, which renders the current view as HTML and pushes it to Pepper's tablet through the robot \texttt{bridge}.

\section{Session Management}
\label{sec:orchestration}

A receptionist session is the unit of interaction with a single visitor.
The voice-agent worker for the currently scheduled condition is connected to the LiveKit room as a warm agent during idle: speech-processing models are already loaded, the LiveKit transport is established, and the agent is waiting for an activation signal.
When a visitor greets Pepper, the session driver sends an activation signal over a LiveKit data channel; the agent greets the visitor, and dialogue begins.
The session ends when the agent fires \texttt{end\_conversation}, or after a silence timeout if the visitor does not respond.
The warm-agent design is a deliberate choice driven by first-response latency: loading the speech-processing models takes several seconds on the target hardware, and keeping the worker alive across the idle state amortizes this cost.

\subsection{Experimental Loop}
\label{sec:experiment_loop}

For the experiment, sessions are dispatched in a loop on the Raspberry~Pi.
The loop runs one session at a time, alternates the assigned condition (Condition~A and Condition~B), and persists the next-up condition and participant identifier to a small JSON state file so the loop can resume after a restart.
